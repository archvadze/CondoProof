# Solana anchoring v1

Program ID: `3TmQGbKRSaTb1r9vabWwWPeMKEXT72AkuyDf4P2Li7gF`.
Target: Solana Devnet. Anchor toolchain and anchor-lang stay at 1.1.2.

## Identities

Building hash: SHA-256 of `condoproof-jcs-v1` canonical UTF-8 JSON:
`{ "domain": "condoproof/building/v1", "buildingId": "<PostgreSQL building UUID>" }`.
Building PDA seeds: UTF-8 `building`, authority public key (32 bytes), building hash (32 bytes).
The authority namespace prevents another signer from occupying the expected PDA. A verifier
must use a trusted configured authority, not accept whichever authority an API supplies.
No on-chain global registrar or real-world ownership attestation is implemented.

Commitment PDA seeds: UTF-8 `commitment`, building PDA (32 bytes), signed proposal signingHash
(32 decoded hex bytes). Do not hash the hex string again.
`record_commitment(proposal_hash, commitment_hash, service_version_hash)` uses decoded SHA-256 digests.
proposal_hash = immutable `Proposal.signingHash`;
commitment_hash = independently verified signed approval payload hash;
service_version_hash = canonical service-version content hash.

## Accounts

BuildingState: discriminator(8), authority(32), building_hash(32), bump(1): 73 bytes.
CommitmentState: discriminator(8), schema_version(1), building(32), proposal_hash(32),
commitment_hash(32), service_version_hash(32), recorded_slot(8), bump(1): 146 bytes.
Program-owned account layout is Anchor/Borsh; IDL is generated by `anchor build`.

## Authorization and immutability

Building creation requires authority signature; every commitment requires the SAME signer via
`has_one`, canonical building seeds and stored bump. The commitment uses `init`, not
`init_if_needed`; repeat creation fails. A client must fetch an existing account and compare
all identity/hash fields before treating a duplicate as successful.
No update, close or authority-rotation instruction exists in v1. All-zero digests fail.
Successful transactions produce an immutable account under this program's instruction set.
The program remains upgradeable unless upgrade authority is separately revoked. Do not claim
irreversibility against future program upgrades.

## Verification boundary

The program anchors hashes submitted by an authorized building writer. It DOES NOT verify
Ed25519 resident signatures or weighted voting on chain. Exported signed proof verification
remains required. This is verifiable off-chain governance with authorized on-chain anchoring.
No names, emails, wallet electorate, UUIDs, documents or full JSON payload are stored on chain.
Authority public key and derived hashes are public.

Future API chain verification must independently check configured Devnet RPC, account owner,
IDL discriminator/schema/length, canonical building+commitment PDA and bumps, registered authority,
all three hashes and building linkage. Read the account at finalized commitment. A transaction
signature alone, or DB status CONFIRMED alone, is insufficient for `onChainVerified: true`.
The stored creation slot is not a wall-clock timestamp.
